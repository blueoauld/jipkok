# 집콕

가까운 거리의 사람들과 쪽지로 대화를 시작하는 위치 기반 채팅 서비스다.

- **앱** - React Native, Expo SDK 57 / **웹** — Next.js 16
- **서버** - Kotlin 2.3, Spring Boot 4.1, Java 25, PostgreSQL 18 + PostGIS, Redis
- **인프라** - AWS EC2 (Graviton), RDS, Cloudflare (R2, Workers, WAF), GitHub Actions

## 아키텍처

![인프라 아키텍처](docs/architecture.png)

모든 요청은 Cloudflare를 거쳐 EC2의 Caddy로 들어가고, Caddy가 Spring Boot 서버로 넘긴다. 서버는 도커 컴포즈로 Caddy, 애플리케이션, Redis 세 컨테이너를 띄운다. 사진은 서버를 거치지 않는다. 클라이언트가 서명된 URL로 R2에 직접 올리고 직접 받아간다.

## 성능 개선

회원 목록이 서비스의 첫 화면이라 여기가 느리면 전부 느리게 느껴진다. 운영과 같은 RDS에 100만 건을 넣고 측정했다.

| 조회          | 개선 전 | 개선 후 | 개선율 |
| ------------- | ------- | ------- | ------ |
| 최신순        | 1192ms  | 6ms     | 99.5% |
| 인기순        | 1173ms  | 40ms    | 96.6% |
| 거리순        | 2897ms  | 120ms   | 95.9% |
| 최신순 + 성별 | 1327ms  | 505ms   | 61.9% |
| 닉네임 검색   | 930ms   | 351ms   | 62.3% |

**인덱스만으로는 최신순과 거리순이 전혀 빨라지지 않았다.** 쿼리를 고쳐야 했다.

최신순은 커서를 표현식으로 비교하고 있었다. 정렬 기준이 컬럼이 아니라 표현식이면 인덱스에 이미 정렬된 순서를 쓰지 못한다. 비교와 정렬을 모두 컬럼 기준으로 바꾸자 1192ms가 6ms가 됐다.

거리순은 `st_distancesphere`로 계산한 값을 정렬에 쓰고 있었다. 이 함수는 모든 행을 계산해야 해서 GiST 인덱스를 타지 못한다. PostGIS의 KNN 연산자 (`<->`)로 정렬을 바꿔 인덱스가
가까운 순서대로 훑도록 했다.

```sql
-- 정렬은 인덱스를 타는 KNN 연산자로
order by geography(st_makepoint(m.longitude, m.latitude))
    <-> geography(st_makepoint(:longitude, :latitude)) asc
```

다만 두 방식은 계산 모델이 달라서 결과가 어긋날 수 있었다. 응답에 담는 거리값은 `st_distancesphere` 그대로 두고 정렬에만 KNN을 쓰기로 하고, 5만 건으로 두 값의 순서가 뒤바뀌는 경우가 있는지 대조해 0건임을 확인한 뒤 적용했다.

**채팅은 측정한 뒤 인덱스를 넣지 않기로 했다.** 메시지 조회는 가장 느린 경우가 11ms, 방 목록은 실제 방 개수 (1~6개)에서 12ms였다. 2000개 방이라는 비현실적인 조건에서야 362ms가 나왔다. 지금 필요하지 않은 인덱스는 쓰기 비용만 늘린다고 판단했다.

## 기술 선택 근거

**사진은 서버를 거치지 않는다** - 업로드와 조회 모두 서명된 URL로 R2에 직접 붙는다. 서버는 URL만 발급한다. 이미지가 서버 메모리와 대역폭을 쓰지 않아 EC2 한 대로 버틸 수 있다. 비공개 사진
(비밀 사진, 신고 증거, 채팅 사진)은 Cloudflare WAF 규칙으로 서명 없는 접근을 막았다.

**소켓 연결 여부로 푸시를 판단한다** - 상대가 채팅방을 보고 있으면 메시지는 웹소켓으로 즉시 도착하므로 푸시를 보내지 않는다. 읽고 있는 화면에 알림이 겹치는 것을 막고 발송량도 줄인다.

**신고는 접수 시점을 통째로 복사한다** - 신고당한 회원의 프로필, 사진 키, 대화 내용을 스냅샷으로 남긴다. 프로필을 지우거나 채팅방을 나가거나 탈퇴해도 증거가 사라지지 않는다.

**검수는 커밋 이후에 비동기로 돌린다** - 자기소개와 코멘트는 OpenAI로 검수하는데, 외부 API 응답을 기다리느라 저장이 늦어지면 안 된다. 커밋 이후 별도 트랜잭션에서 검수하고, 부적절하면 그때 내용을
안내 문구로 바꾼다.

**감사 기록은 보상 테이블과 분리했다** - 접속 기록은 이미 접속 보상 테이블에 IP까지 남고 있었지만, 그 테이블은 보상 정책이 바뀌면 함께 바뀐다. 수사 협조에 쓰이는 기록이 정책에 좌우되면 안 되므로 별도
테이블로 두고 90일 뒤 지운다.

**관리 도구는 디스코드 봇으로 만들었다** - 관리자 웹을 따로 만드는 대신 슬래시 명령으로 정지, 해제, 신고 조회, 프로필 초기화를 처리한다. 알림을 받는 곳에서 바로 조치할 수 있고, 인증과 권한은 디스코드
역할로 해결된다.

## 테스트

334건이 돌고, 통과해야 배포된다. 대부분은 목으로 의존성을 끊은 서비스 테스트(26개
클래스)고, 목으로는 확인할 수 없는 것만 실제 DB를 띄워 검증한다.

**쿼리는 목으로 검증할 수 없다.** 성능 때문에 고쳐 쓴 목록 쿼리는 네이티브 SQL이라
문자열이 맞는지가 아니라 결과가 맞는지를 봐야 한다. 커서 페이징이 경계에서
빠뜨리거나 중복하지 않는지, 차단한 회원이 목록에서 빠지는지, 거리순 정렬이 실제
거리와 일치하는지를 DB에 데이터를 넣고 확인한다.

**테스트 이름은 한글 문장으로 쓴다.** 무엇을 보장하는지가 이름만으로 읽히도록 했다.

```kotlin
fun `같은 번호로 오늘 이미 출석했으면 보상을 주지 않는다`()
fun `자기 자신에게는 좋아요를 누를 수 없다`()
fun `출석 날짜는 한국 시간을 따른다`()
```

**시간과 무작위는 주입해서 고정한다.** 출석 보상은 한국 시간 기준 날짜가 바뀌는
지점이 중요한데, 시스템 시계를 쓰면 자정 근처에서만 실패하는 테스트가 된다.
`Clock`을 주입해 특정 시각으로 고정했다.

**엣지 케이스를 우선 덮었다.** 자기 자신에게 좋아요, 남의 사진 키로 업로드, 다른
방의 메시지에 답글, 이미 가려진 글 재검수, 참여자가 아닌 방 조회처럼 실수하기
쉬운 경로에 테스트를 붙였다.

## 운영 자동화

**배포** - main에 푸시하면 테스트를 돌리고, 러너에서 jar를 만들어 arm64 이미지로 GHCR에 올린 뒤 EC2에서 교체한다. 경로 필터를 걸어 서버가 바뀌지 않은 푸시에는 배포가 돌지 않는다. 실행
결과 화면에 테스트 통과 수와 실패한 테스트 이름을 남긴다.

**장애 감지** - 두 경로로 디스코드에 모인다.

- 서버가 죽으면 UptimeRobot이 밖에서 `/health`를 확인하고 알린다. 서버가 스스로 알릴 수 없는 상황을 밖에서 감시해야 하기 때문이다
- 에러가 나면 로그백 어펜더가 스택과 함께 보낸다. 요청을 처리하다 난 500뿐 아니라 검수나 푸시처럼 응답에 드러나지 않는 실패도 잡힌다

에러 알림에는 두 가지 안전장치를 뒀다. 디스코드 전송이 실패해 다시 전송을 부르는 고리를 끊기 위해 디스코드 관련 로거는 제외하고, 같은 에러가 쏟아질 때 웹훅이 차단되지 않도록 분당 5건으로 제한한다.

**무중단 배포** - graceful shutdown으로 처리 중인 요청을 끝내고 종료한다. 배포할 때마다 이전 이미지를 정리해 디스크가 차지 않게 한다.

## 문제 해결 기록

**배포한 이미지가 EC2에서 실행되지 않았다** - EC2가 Graviton (arm64)인데 러너에서 빌드한 이미지는 amd64였다. 러너에서 jar까지만 만들고 이미지 빌드는
`platforms: linux/arm64`로 지정해 해결했다.

**컨테이너 헬스체크가 항상 실패했다** - `/dev/tcp`를 쓰는 검사가 도커의 `CMD-SHELL`
아래에서 동작하지 않았다. 셸이 bash가 아니라 dash였고, 이미지가 Alpine이라 bash도 없었다. `nc -z`로 바꿨다.

**광고 보상이 지급되지 않았다** - AdMob 콜백을 처리하고 204를 돌려주고 있었는데, 구글은 200을 기대한다고 문서에 적혀 있었다. 응답 코드만 바꿔 해결했다.

**관계없는 항목을 수정해도 재검수됐다** - 코멘트가 부적절해 가려진 상태에서 자기소개만 고쳐도 코멘트가 다시 검수 대상이 됐다. 원본을 따로 보관하는 대신 가린 문구로 덮어쓰고, 이미 가려진 글은 검수하지 않도록
바꿨다.

**이벤트 리스너가 뜨지 않았다** - `@TransactionalEventListener`에 `@Transactional`을 같이 붙이면 `REQUIRES_NEW`가 아닌 경우 등록되지 않는다. 커밋 이후에 도는
리스너라 기존 트랜잭션이 이미 끝났기 때문이다.
