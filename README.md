# 집콕

가까운 거리의 사람들과 쪽지로 대화를 시작하는 위치 기반 채팅 서비스다. 한국, 일본, 대만에서 가입할 수 있고 한국어, 일본어, 중국어(번체), 영어를 지원한다.

- **앱** - React Native, Expo SDK 57 / **웹, 어드민** — Next.js 16
- **서버** - Kotlin 2.3, Spring Boot 4.1, Java 25, PostgreSQL 18 + PostGIS, Redis
- **인프라** - AWS EC2 (Graviton), RDS, Cloudflare (R2, Workers, WAF), GitHub Actions

## 아키텍처

![인프라 아키텍처](docs/architecture.png)

모든 요청은 Cloudflare를 거쳐 EC2의 Caddy로 들어가고, Caddy가 Spring Boot 서버로 넘긴다. 서버는 도커 컴포즈로 Caddy, 애플리케이션, Redis 세 컨테이너를 띄운다. 사진은 서버를 거치지 않는다. 클라이언트가 서명된 URL로 R2에 직접 올리고 직접 받아간다.

### 코드 구조

한 저장소에 네 프로젝트가 있다.

| 경로 | 내용 |
| --- | --- |
| `app/` | React Native 앱. Expo Router 화면, TanStack Query 훅, 레트로 디자인 시스템 |
| `server/` | Spring Boot API 서버 |
| `admin/` | 운영용 웹. Cloudflare Access 뒤에 둔다 |
| `web/` | 홈페이지와 약관 |

서버는 도메인 우선으로 나눈다. `domain/` 아래 20개 도메인(member, chat, feed, worry, report, suspension, point 등)이 각각 `web`, `service`, `repository`, `entity`, `dto`를 갖고, `global/`에는 도메인을 모르는 공통 계층(보안, 저장소, 디스코드, 설정)만 둔다. 방향이 무너지지 않도록 세 가지 규칙을 지킨다.

- **`global`은 `domain`을 import하지 않는다.** 도메인 이벤트를 듣는 리스너는 디스코드로 보내는 것이라도 그 도메인의 `service`에 둔다
- **admin 전용 쿼리는 `admin/repository`에 둔다.** 목록, 카운트, 대시보드 통계가 도메인 리포지토리에 섞이면 도메인이 admin을 알게 된다. admin 밖의 도메인은 admin을 import하지 않는다
- **admin의 쓰기 작업은 도메인 서비스에 위임한다.** 리포지토리를 직접 만지면 도메인의 삭제 규칙(카운트 차감 같은 부수 작업)과 어긋날 수 있다. 모든 조치는 행위자와 함께 `admin_action` 테이블에 남는다

**API 계약은 커밋된 스냅샷으로 관리한다.** springdoc이 만드는 OpenAPI 문서를 `app/openapi.json`과 `admin/openapi.json`으로 저장소에 두고, 앱은 openapi-typescript로 요청과 응답 타입을 생성한다. 서버가 내놓는 문서와 스냅샷이 어긋나면 테스트가 실패하므로, API를 바꿔놓고 클라이언트 타입을 낡은 채 두는 실수가 커밋 단계에서 잡힌다.

## 성능 개선

회원 목록이 서비스의 첫 화면이라 여기가 느리면 전부 느리게 느껴진다. 운영과 같은 RDS에 100만 건을 넣고 측정했다.

| 조회          | 개선 전 | 개선 후 | 개선율 |
| ------------- | ------- | ------- | ------ |
| 최신순        | 1192ms  | 6ms     | 99.5% |
| 인기순        | 1173ms  | 40ms    | 96.6% |
| 거리순        | 2897ms  | 120ms   | 95.9% |
| 최신순 + 성별 | 1327ms  | 505ms   | 61.9% |
| 닉네임 검색   | 930ms   | 351ms   | 62.3% |

**인덱스만으로는 최신순과 거리순이 전혀 빨라지지 않았다.** 쿼리를 고쳐야 했다.

최신순은 커서를 표현식으로 비교하고 있었다. 정렬 기준이 컬럼이 아니라 표현식이면 인덱스에 이미 정렬된 순서를 쓰지 못한다. 비교와 정렬을 모두 컬럼 기준으로 바꾸자 1192ms가 6ms가 됐다.

거리순은 `st_distancesphere`로 계산한 값을 정렬에 쓰고 있었다. 이 함수는 모든 행을 계산해야 해서 GiST 인덱스를 타지 못한다. PostGIS의 KNN 연산자 (`<->`)로 정렬을 바꿔 인덱스가
가까운 순서대로 훑도록 했다.

```sql
-- 정렬은 인덱스를 타는 KNN 연산자로
order by geography(st_makepoint(m.longitude, m.latitude))
    <-> geography(st_makepoint(:longitude, :latitude)) asc
```

응답에 담는 거리값은 `st_distancesphere` 그대로 두고 정렬에만 KNN을 썼다. 두 방식이 어긋날까 봐 5만 건으로 순서를 대조해 0건임을 확인한 뒤 적용했는데, 나중에 값을 직접 재보니 애초에 어긋날 수 없는 조합이었다. geography의 `<->`는 타원체가 아니라 구로 계산해서 `st_distancesphere`와 같은 값을 낸다.

| 8km 구간 | 값 |
| --- | --- |
| `st_distancesphere` | 9058.96 |
| `geography <->` | 9058.955 |
| `ST_Distance(geography, ...)` | 9055.85 |

타원체를 쓰는 것은 세 번째뿐이고 이 코드베이스는 그것을 쓰지 않는다. 표시값과 정렬 기준이 같은 계산이라 순서가 뒤바뀔 여지가 없다.

**목록 세 개는 정렬 키가 인덱스를 벗어나 있었다.** 채팅방, 고민, 피드를 각각 재보니 원인이 같았다. 필요한 것은 스무 개인데 정렬 키가 필터와 다른 곳에 있어 인덱스로 정렬을 만들지 못하고, 대량을 훑어 버린 뒤 스무 개를 건지고 있었다.

| 조회 | 조건 | 개선 전 | 개선 후 |
| --- | --- | --- | --- |
| 채팅방 목록 | 방 500개, 첫 페이지 | 0.52ms | 0.02ms |
| 고민 공감순 | 분류가 전체의 4% | 4.86ms | 0.01ms |
| 고민 댓글순 | 분류가 전체의 4% | 1.72ms | 0.02ms |
| 피드 목록 | 이틀 전 날짜 | 6.89ms | 0.05ms |

**채팅방 목록**은 정렬 키 `last_message_id`가 `chat_room`에 있는데 필터는 `chat_room_member`에서 시작했다. 방 500개를 전부 조인해 정렬한 뒤 스무 개를 잘랐고, 커서 페이징인데도 뒤 페이지가 싸지지 않았다. 방 멤버 쪽에 마지막 메시지를 비정규화하고 `(member_id, last_message_id desc)`를 걸어 스무 개만 읽고 멈추게 했다. 읽은 버퍼가 3514에서 41이 됐다.

**고민 목록**은 분류 필터를 붙이면서 인덱스를 미뤄뒀던 자리다. "일곱 갈래니 일곱 배쯤 더 읽겠지"로 봤는데 최신순만 생각한 판단이었다. 공감 수는 값 종류가 60개뿐이라 같은 값이 길게 이어지고, 그 안에서 4%짜리 분류를 찾느라 스무 개를 얻는 데 인덱스 항목 2만 5천 개를 버리고 있었다. 정렬용 복합 인덱스 두 개를 넣었다. 최신순용은 넣지 않았다. 없어도 0.036ms인데 최신순이 기본 정렬이라 가장 잦은 쓰기 경로에 유지 비용만 붙는다.

**피드 목록**은 인덱스를 만들지 않고 정렬 두 줄만 고쳤다. `order by id desc`가 기본 키를 거꾸로 훑으며 날짜에 안 맞는 글을 버려서, 날짜를 거스를수록 선형으로 느려졌다. 화면에 날짜 선택기가 있어 실제로 과거를 본다. `slot_at`은 글을 쓸 때 현재 시각을 시간 단위로 자른 값이라 id와 항상 같은 방향으로 늘어난다. 정렬을 `slot_at desc, id desc`로 바꾸자 이미 있던 `(slot_at, id)` 인덱스를 타면서 결과 순서는 그대로 남았다.

의심했던 차단 필터는 문제가 아니었다. 차단 700건인 사용자와 없는 사용자가 6.66ms 대 6.69ms로 같았다. 양방향 인덱스가 이미 있어 `BitmapOr`로 한 행당 0.003ms에 끝난다.

**채팅 메시지는 측정한 뒤 인덱스를 넣지 않기로 했다.** 메시지 조회는 가장 느린 경우가 11ms, 방 목록은 실제 방 개수 (1~6개)에서 12ms였다. 2000개 방이라는 비현실적인 조건에서야 362ms가 나왔다. 지금 필요하지 않은 인덱스는 쓰기 비용만 늘린다고 판단했다.

## 설계 결정

### 사진

**사진은 서버를 거치지 않는다** - 업로드와 조회 모두 서명된 URL로 R2에 직접 붙는다. 서버는 URL만 발급한다. 이미지가 서버 메모리와 대역폭을 쓰지 않아 EC2 한 대로 버틸 수 있다. 비공개 사진
(비밀 사진, 신고 증거, 채팅 사진)은 Cloudflare WAF 규칙으로 서명 없는 접근을 막았다.

**대신 크기는 올라온 뒤에 확인한다** - 서명된 PUT URL은 크기를 제한하지 못한다. 서명에 담기는 것은 버킷과 키와 콘텐츠 타입뿐이라, 발급받은 URL로 `image/jpeg`라고 하면서 아주 큰 파일을 올려도 막을 수 없다. S3에는 정책으로 상한을 거는 presigned POST가 있지만 R2는 지원하지 않는다. 그래서 키를 확정하는 시점에 저장소에 크기를 물어 상한을 넘으면 객체를 지우고 거절한다. 이미 전송된 뒤라 완벽하지 않지만 R2는 인그레스가 무료라 실질 손해는 저장 공간뿐이고 그것도 회수된다. 아무것도 올리지 않은 채 키만 보내는 것도 이 확인에 걸린다.

### 익명 게시판

**차단 필터를 일부러 걸지 않았다** - 고민 게시판은 응답에 회원 번호도 닉네임도 성별도 담지 않는다. 그런데 차단 목록으로 글을 걸러주면 익명이 깨진다. 누군가를 차단하기 전후로 목록을 비교하면 어느 글이 사라졌는지 보이고, 그것이 곧 글쓴이다. 다른 목록에는 다 걸려 있는 필터를 여기서만 뺐다. 내가 신고한 글을 숨기는 것은 남겨뒀는데, 그것은 내가 이미 그 글을 지목한 뒤라 새로 알려주는 정보가 없다.

**같은 이유로 익명 번호는 지운 댓글까지 센다** - 글마다 익명1, 익명2로 번호를 매기는데, 지운 댓글을 빼고 세면 번호가 앞으로 당겨진다. 그러면 서로 다른 사람이 같은 번호를 쓰게 되어 대화가 뒤섞인다. 소프트 삭제된 행까지 포함해 세도록 네이티브 쿼리로 두었다.

### 신고

**신고 정책은 게시판마다 다르게 잡았다** - 피드 게시물은 다섯 번 신고되면 자동으로 지운다. 고민 글은 다섯 번이면 알림만 보내고 지우는 것은 운영자가 판단한다. 고민은 내용이 무거워 신고가 악의로 몰릴 수 있고, 잘못 지우면 되돌릴 수 없기 때문이다. 반대로 고민 댓글은 자동 삭제한다. 글보다 가볍고 수가 많아 사람이 일일이 볼 수 없다.

**신고는 접수 시점을 통째로 복사한다** - 신고당한 회원의 프로필, 사진 키, 대화 내용을 스냅샷으로 남긴다. 프로필을 지우거나 채팅방을 나가거나 탈퇴해도 증거가 사라지지 않는다.

### 어뷰징 방어

**로그인 제한은 번호와 IP에 다르게 건다** - 10분에 번호 5회, IP 30회다. 국내 이동통신이 CGNAT를 써서 여러 사용자가 같은 IP를 공유하므로 IP 쪽을 느슨하게 뒀다. 확인은 BCrypt 앞에 둔다. 한도를 넘으면 해시 검증을 아예 하지 않아 시도 폭주가 CPU를 갉아먹는 경로도 함께 막힌다.

**인증번호 발송에는 전체 상한을 하나 더 뒀다** - 번호당, IP당 한도는 분산 IP로 번호를 바꿔가며 발송하는 과금 공격을 막지 못한다. 하루 전체 500건을 넘으면 발송을 멈추고 디스코드로 한 번 알린다. 최악의 손해가 국제 SMS 하루치 비용으로 잘린다.

### 트랜잭션과 비동기

**트랜잭션 안에서 외부를 호출하지 않는다** - R2 복사, Expo 푸시, OpenAI 검수가 모두 트랜잭션 안에 있었다. 커넥션 풀은 10개인데 신고 하나가 R2 왕복 수십 번 동안 커넥션을 물고 있었다. 게다가 되돌릴 수 없는 작업을 트랜잭션에 넣어도 롤백 안전성은 얻지 못한다. 복사가 끝난 뒤 커밋이 실패하면 R2에 고아 객체만 남는다. 커밋을 먼저 하고 외부 작업을 뒤로 미뤘다. 그러면 실패해도 "있어야 할 것이 없다"로 남아 재시도할 수 있다. 반대 순서면 아무도 모르는 고아가 남는다.

**검수는 커밋 이후에 비동기로 돌린다** - 자기소개와 코멘트는 OpenAI로 검수하는데, 외부 API 응답을 기다리느라 저장이 늦어지면 안 된다. 커밋 이후 비동기로 검수하고, 부적절하면 그때 내용을
안내 문구로 바꾼다. 읽기와 쓰기만 짧게 트랜잭션을 잡고 검수 호출은 그 밖에서 한다.

**소켓 연결 여부로 푸시를 판단한다** - 상대가 채팅방을 보고 있으면 메시지는 웹소켓으로 즉시 도착하므로 푸시를 보내지 않는다. 읽고 있는 화면에 알림이 겹치는 것을 막고 발송량도 줄인다.

### 데이터와 운영

**탈퇴는 한 파일에 모으고 테스트로 지킨다** - 탈퇴가 지워야 할 데이터가 채팅, 피드, 고민, 포인트 등 열두 도메인에 걸쳐 있다. 도메인별 이벤트로 흩뿌리면 파일은 깔끔해지지만 리스너 하나를 빠뜨려도 조용히 고아 데이터가 남고, 카운트 차감 뒤 삭제라는 순서도 암묵이 된다. 순서가 눈에 보이는 중앙 서비스를 유지하고, 대신 모든 도메인에 데이터를 심은 회원을 탈퇴시켜 흔적이 남지 않는지 확인하는 통합 테스트를 붙였다. 새 도메인에서 정리를 빠뜨리면 구조와 무관하게 테스트가 잡는다.

**감사 기록은 보상 테이블과 분리했다** - 접속 기록은 이미 접속 보상 테이블에 IP까지 남고 있었지만, 그 테이블은 보상 정책이 바뀌면 함께 바뀐다. 수사 협조에 쓰이는 기록이 정책에 좌우되면 안 되므로 별도
테이블로 두고 90일 뒤 지운다.

**관리 도구는 어드민 웹으로 옮겼다** - 처음에는 디스코드 봇 슬래시 명령으로 처리했지만, 대시보드와 목록 화면이 필요해지면서 `admin/`에 별도 웹을 만들었다. 정지, 해제, 신고 처리, 프로필 초기화,
탈퇴, 피드 삭제를 웹에서 하고 모든 조치는 행위자와 함께 `admin_action` 테이블에 남는다. 봇은 신고 접수, 피드 자동 삭제, 검수, 에러 알림만 보낸다. 바깥은 Cloudflare Access로 막고 안쪽은
기존 휴대폰 로그인에 관리자 역할을 더해 쓴다.

## 테스트

689건이 돌고, 통과해야 배포된다. 98개 테스트 클래스 중 75개는 목으로 의존성을 끊은
서비스 테스트고, 나머지 23개는 목으로 확인할 수 없는 것만 실제 DB와 Redis를 띄워
검증한다. 컨테이너는 Testcontainers가 테스트 안에서 띄우므로 미리 준비해둘 것이
없고, 이미지 버전이 코드에 고정돼 로컬과 CI가 같은 것을 쓴다.

**쿼리는 목으로 검증할 수 없다.** 성능 때문에 고쳐 쓴 목록 쿼리는 네이티브 SQL이라
문자열이 맞는지가 아니라 결과가 맞는지를 봐야 한다. 커서 페이징이 경계에서
빠뜨리거나 중복하지 않는지, 차단한 회원이 목록에서 빠지는지, 거리순 정렬이 실제
거리와 일치하는지를 DB에 데이터를 넣고 확인한다.

**테스트 이름은 한글 문장으로 쓴다.** 무엇을 보장하는지가 이름만으로 읽히도록 했다.

```kotlin
fun `같은 번호로 오늘 이미 출석했으면 보상을 주지 않는다`()
fun `자기 자신에게는 좋아요를 누를 수 없다`()
fun `모든 도메인에서 회원의 흔적을 지운다`()
```

**시간과 무작위는 주입해서 고정한다.** 출석 보상은 한국 시간 기준 날짜가 바뀌는
지점이 중요한데, 시스템 시계를 쓰면 자정 근처에서만 실패하는 테스트가 된다.
`Clock`을 주입해 특정 시각으로 고정했다.

**엣지 케이스를 우선 덮었다.** 자기 자신에게 좋아요, 남의 사진 키로 업로드, 다른
방의 메시지에 답글, 이미 가려진 글 재검수, 참여자가 아닌 방 조회처럼 실수하기
쉬운 경로에 테스트를 붙였다.

## 운영 자동화

**배포** - main에 푸시하면 린트와 테스트를 돌리고, 러너에서 jar를 만들어 arm64 이미지로 GHCR에 올린 뒤 EC2에서 교체한다. 경로 필터를 걸어 서버가 바뀌지 않은 푸시에는 배포가 돌지 않는다. 실행
결과 화면에 테스트 통과 수와 실패한 테스트 이름을 남긴다.

**장애 감지** - 두 경로로 디스코드에 모인다.

- 서버가 죽으면 UptimeRobot이 밖에서 `/health`를 확인하고 알린다. 서버가 스스로 알릴 수 없는 상황을 밖에서 감시해야 하기 때문이다. 액추에이터가 DB와 Redis 연결까지 확인하므로 프로세스는 떠 있는데 의존 자원이 끊긴 상태도 잡힌다
- 에러가 나면 로그백 어펜더가 스택과 함께 보낸다. 요청을 처리하다 난 500뿐 아니라 검수나 푸시처럼 응답에 드러나지 않는 실패도 잡힌다

에러 알림에는 두 가지 안전장치를 뒀다. 디스코드 전송이 실패해 다시 전송을 부르는 고리를 끊기 위해 디스코드 관련 로거는 제외하고, 같은 에러가 쏟아질 때 웹훅이 차단되지 않도록 분당 5건으로 제한한다.

**무중단 배포** - graceful shutdown으로 처리 중인 요청을 끝내고 종료한다. 배포할 때마다 이전 이미지를 정리해 디스크가 차지 않게 한다.

## 문제 해결 기록

**배포한 이미지가 EC2에서 실행되지 않았다** - EC2가 Graviton (arm64)인데 러너에서 빌드한 이미지는 amd64였다. 러너에서 jar까지만 만들고 이미지 빌드는
`platforms: linux/arm64`로 지정해 해결했다.

**컨테이너 헬스체크가 항상 실패했다** - `/dev/tcp`를 쓰는 검사가 도커의 `CMD-SHELL`
아래에서 동작하지 않았다. 셸이 bash가 아니라 dash였고, 이미지가 Alpine이라 bash도 없었다. `nc -z`로 바꿨다.

**광고 보상이 지급되지 않았다** - AdMob 콜백을 처리하고 204를 돌려주고 있었는데, 구글은 200을 기대한다고 문서에 적혀 있었다. 응답 코드만 바꿔 해결했다.

**관계없는 항목을 수정해도 재검수됐다** - 코멘트가 부적절해 가려진 상태에서 자기소개만 고쳐도 코멘트가 다시 검수 대상이 됐다. 원본을 따로 보관하는 대신 가린 문구로 덮어쓰고, 이미 가려진 글은 검수하지 않도록
바꿨다.

**이벤트 리스너가 뜨지 않았다** - `@TransactionalEventListener`에 `@Transactional`을 같이 붙이면 `REQUIRES_NEW`가 아닌 경우 등록되지 않는다. 커밋 이후에 도는
리스너라 기존 트랜잭션이 이미 끝났기 때문이다.

**만료된 기기 토큰이 한 번도 지워지지 않고 있었다** - Expo가 `DeviceNotRegistered`로 알려준 토큰을 지우는 코드는 있었는데 반영되지 않았다. 채팅 푸시는 `AFTER_COMMIT` 리스너에서 보내는데, 그
시점에는 이미 커밋된 트랜잭션의 자원이 스레드에 그대로 묶여 있다. 그래서 `REQUIRED`로 들어간 삭제가 끝난 트랜잭션에 합류해 실행만 되고 버려졌다. 예외도 로그도 남지 않아 정적으로는 보이지 않는다.
프로브로 재보니 같은 자리에서 `REQUIRES_NEW`는 커밋되고 `REQUIRED`는 버려졌다. 쓰기 지점마다 `REQUIRES_NEW`를 명시하고 실제 DB로 회귀 테스트를 붙였다.

**`@Async`가 작업마다 새 스레드를 만들고 있었다** - `applicationTaskExecutor` 빈이 아예 없었다. WebSocket 메시징이 `Executor` 빈을 먼저 만들어 Boot가 생성을 포기했고, `@Async`는
`SimpleAsyncTaskExecutor`로 떨어져 있었다. 푸시, 검수, 사진 복사가 전부 여기 얹혀 있었다. 실행자를 코드로 명시해 묶었다.

**테스트 설정이 서버 설정을 통째로 가리고 있었다** - `src/test/resources/application.yaml`은 이름이 같아 `src/main`의 것을 덮는다. 메인에 넣은 설정이 테스트에서만 조용히 빠졌다. 겹치는 설정을
메인으로 모으고 테스트 것은 `application-test.yaml`로 옮겨 이름이 부딪히지 않게 했다.
